The governed demo flow

The demo separates supporting AI work from investment authority. Evidence must be admitted, analysis must be grounded and cited, human reviews are version-bound, and the final output remains a draft committee pack.

Run analysis

Human review

Deal, Legal, and Compliance approvals bind to the exact authoritative version.

Prepare draft

What is needed

Local presentation has a short dependency list. Azure activation adds identity, infrastructure, evidence authority, and operational ownership.

Local prerequisites

  • Windows PowerShell or PowerShell 7
  • Node.js 22–26 with npm
  • Azure CLI with Bicep support for offline compilation

Controlled Azure deployment

The infrastructure code is compiled and tested, but no cloud resources have been deployed. Treat deployment as a separately authorized release activity.

Replace development placeholders with approved resource IDs, private endpoints, image digests, scopes, and route versions.

5

Authorize and deploy

Obtain explicit release approval, run Azure login and what-if, deploy Bicep, then execute controlled runtime smoke tests.

Approved standalone topology

This development deployment is constrained to MoA-Sub2 (8364fb4d-2d36-4da5-908b-36cb8b808b8c), tenant 27140306-eea5-4e7f-91e9-4c9e86864b3a, westeurope, and stratton-demo-rg. It is a controlled development environment, not a production-resilience claim.

Public web, private services

  • The public web Container App is the only browser-facing application endpoint.
  • The internal BFF and internal Phase 5 API are reachable only through the Container Apps network.
  • Backend for Frontend (BFF) means a small server tailored to the web app: it validates the user token, applies governance rules, and makes internal calls on the browser’s behalf.
  • Phase 5 remains authoritative for bundles, reviews, draft preparation, and approved route evidence; no investment-decision or committee-submission endpoint is added.

Private and governed boundaries

  • Azure SQL has public network access disabled and is reached through its private endpoint using Microsoft Entra authentication.
  • Container App managed identities receive only the required SQL, registry, evidence, messaging, Search, Document Intelligence, Azure OpenAI, and ARM Reader permissions; no application secret is stored.
  • One Azure OpenAI account hosts the three separately governed deployments: Luna, Terra, and Sol. Each route retains pinned version and tenant-scoped evidence that must agree with live ARM metadata.
  • The minimum-cost development posture uses the smallest suitable development SKUs, serverless SQL auto-pause, and scale-to-zero where startup behaviour permits.

Seven controlled deployment stages

Every stage is incremental and fail closed. A required dependency, identity, route, tenant, network, migration, or configuration mismatch stops the next action.

1

Preflight

Confirm subscription, tenant, deployment identity, policy, providers, naming, region, SKU, Azure OpenAI model availability, and quota without making changes.

2

Platform foundation

Approve the foundation Azure what-if, then create the resource group, network, managed identities, private data services, observability, registry, and Azure OpenAI resources without application revisions.

3

Entra foundation

Create or reconcile the SPA, BFF, and Phase 5 registrations, permissions, consent, federated credential, and non-secret identifiers.

4

Image build

Build web, BFF, and Phase 5 images through ACR, then resolve and record immutable SHA-256 digests.

5

Data-plane bootstrap

Apply authorised Entra SQL migrations, create the Search index, and insert the tenant-scoped Luna, Terra, and Sol route-evidence records.

6

Application deployment

Approve the application Azure what-if using real Entra IDs and immutable image digests, then deploy the public web, internal BFF, and internal Phase 5 applications.

7

Verification

Verify health, ingress, sign-in, token validation, OBO, managed-identity completion, private SQL, route authority, and the complete Project Danube presenter flow.

Approval and fail-closed controls

  • Review the exact Azure what-if before each resource stage; it must contain only approved intended changes and no deletes.
  • No provider registration, deployment, or destructive operation proceeds without the separately required explicit approval.
  • Reject placeholder IDs, mutable tags, missing digests, broad RBAC, secret-bearing settings, public SQL, and fallback AI routes.
  • After deployment, execute Project Danube end to end: admit the synthetic evidence, run the cited analysis, complete human reviews, and confirm committee submission remains disabled.
