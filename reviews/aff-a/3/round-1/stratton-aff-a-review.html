Verdict rationale

One unresolved MAJOR feasibility and implementation-readiness finding remains: the Backup vault is selected without a supported workload/policy boundary. AFF-A rules make an unresolved major a DIVERGES verdict. This is not approval, waiver or certification.

Findings

IDSeverityFindingBounded remediation
AFFA-P3-R1-MAJ-001MAJORBackup vault is selected without a supported protected workload or policy boundary.
The design adds a Microsoft.DataProtection/backupVaults resource and lists Azure Backup vault as part of SBB-16, but the reviewed contracts do not bind that vault to a Microsoft-supported protected workload, backup policy, restore path or owner. Azure SQL Database is already covered by service automated PITR/LTR/failover patterns; treating a Data Protection Backup vault as a generic regional backup control is not implementation-ready and can lead AFF-4 to deploy an unsupported or unused recovery component.		Either remove the Backup vault from SBB-16/resource inventory, or explicitly bind it to supported workloads such as Blob backup with policy, retention, restore, region and ownership details. Keep Azure SQL recovery on automated backups/LTR/failover groups unless a supported Azure Backup workload is introduced.
AFFA-P3-R1-MIN-001MINORPrivate-only Application Gateway opt-in is not carried as an AFF-4 fail-closed input.
The design correctly chooses a private-only Application Gateway WAF_v2 ingress, but the handoff does not carry the required subscription feature opt-in/registration check as a fail-closed implementation input. Microsoft Learn says private IP-only Application Gateway v2 controls are generally available and production-supported, but use requires opting in to the experience; missing this gate could block deployment late.		Add the Application Gateway private deployment feature opt-in/registration state and subscription evidence to required AFF-4 inputs or preflight checks before private ingress deployment.
